# CoffeeLink iOS 原生高保真实现设计

日期：2026-08-14

状态：已确认

目标平台：iPhone，iOS 17+

实现技术：Swift 6、SwiftUI、Xcode 16.3

## 1. 目标

在 `ios` 目录中实现可独立运行的 CoffeeLink 原生 iPhone App。现有 `coffeelink` React/Vite 原型是本轮视觉、内容、布局、动效和交互的唯一基准；PRD 用于补充业务语义和状态边界。

首版使用本地 Mock 数据与本地持久化，不连接真实后端、短信、支付或腾讯会议服务，但应完整演示现有原型中的核心业务流程。

## 2. 交付范围

### 2.1 核心页面

1. 发现首页
2. 分享者详情
3. 发起邀请
4. 邀请付款
5. 邀请与对谈列表
6. 邀请或对谈详情
7. 我的
8. 分享中心

### 2.2 认证流程

- 密码登录
- 新用户注册
- 找回密码
- 触发登录后返回原业务位置
- 保留登录前尚未提交的邀请内容

### 2.3 业务弹层与辅助流程

- 腾讯会议入口
- 外观与主题设置
- 编辑公开资料
- 管理分享主题
- 选择签名饮品
- 主题互换设置
- 接受邀请
- 婉拒邀请
- 完成反馈
- 投诉与售后
- 支付成功、失败和取消状态

### 2.4 可交互状态

- 电子咖啡邀请与主题互换两种发起路径
- 邀请提交、待回应、接受、婉拒、要求重选时间、过期和取消
- 电子咖啡接受后付款、已预约、已完成、售后中和已取消
- 主题互换接受后排期、完成和取消
- 分享资料、主题、饮品、时间、会议链接和互换设置修改
- 登录状态、分享开放状态和本地数据恢复

## 3. 非目标

- 不实现 NestJS API、数据库或远程账号系统。
- 不发送真实短信验证码。
- 不调用微信支付、支付宝或腾讯会议 SDK。
- 不接入推送、实名认证、Keychain、埋点或生产级安全策略。
- 不改变现有 Web 原型。
- 不在本轮重新设计 CoffeeLink 的视觉风格。

## 4. 实现路径

采用纯 SwiftUI 原生实现，不使用 `WKWebView`，也不把 React 页面嵌入原生容器。

选择纯 SwiftUI 的原因：

- 满足 iPhone 原生 App 的产品方向。
- 后续可以直接替换 Mock 数据源并接入真实 API。
- 可以使用 XCTest、XCUITest 和模拟器截图进行持续回归。
- 可以正确处理 Safe Area、键盘、动态页面状态和原生导航生命周期。

## 6. 导航设计

- 根视图使用三个 Tab：发现、对谈、我的。
- Tab 内部路由使用 `NavigationStack` 与类型安全的 `AppRoute`。
- 原型中的认证和业务弹层使用 SwiftUI `sheet`、`fullScreenCover` 或自定义覆盖层实现，并按视觉基准选择展示方式。
- 底部 Tab Bar 采用自定义 SwiftUI 组件，以复刻原型尺寸、颜色、未读红点和选中效果。
- 详情、邀请、付款和分享中心页面隐藏 Tab Bar，与 Web 原型保持一致。

## 7. 状态与数据流

`AppStore` 是单一应用状态源，使用 Observation 管理以下状态：

- 当前用户与登录状态
- 分享配置
- 分享者列表
- 邀请与对谈列表
- 当前路由和认证返回动作
- 当前展示的弹层

页面只读取所需状态，并通过明确的 Store 方法触发业务变化。例如：

```text
邀请表单
  → AppStore.submitInvitation
  → 新增待回应记录
  → 跳转对谈详情

接受电子咖啡邀请
  → AppStore.acceptInvitation
  → 状态变为待付款
  → 发起人进入付款页
  → 模拟付款成功
  → 状态变为已预约
```

Mock 数据以 Swift 类型定义，初次启动时载入；用户产生的状态写入本地 JSON。提供仅用于开发和测试的“恢复演示数据”能力，保证截图测试可重复。

## 8. 视觉复刻规则

- 基准视口为原型审计使用的 `393 × 852`。
- 保留原型当前深色主题、咖啡橙强调色、卡片边框、圆角、阴影、渐变和层级关系。
- 文案、示例人物、主题、饮品、金额和状态标签与 Web 原型保持一致。
- 使用自定义 SwiftUI 组件复刻原型，不用系统默认样式替代可见外观。
- 原生 Safe Area、状态栏、Home Indicator 和键盘避让必须正确工作，但不得破坏参考布局。
- 点击区域可以扩展到至少 44pt，视觉尺寸仍按原型呈现。
- 动效复刻原型的淡入、按压、弹层和页面切换节奏；在系统开启“减少动态效果”时降低动画。
- SwiftUI 与浏览器的字体栅格化、系统状态栏图标和原生控件底层行为存在不可避免的像素差异，不将这些差异误报为完全一致。

## 9. 表单与错误处理

- 登录、注册和找回密码使用原型字段、占位文案和按钮状态。
- 手机号、验证码、密码一致性和协议勾选在本地模拟校验。
- 邀请必须选择主题、填写问题并选择时间后才能提交。
- 主题互换必须满足开放分享与拥有主题的条件。
- 模拟支付支持成功、取消和失败后重试。
- 所有错误使用与原型一致的内联提示、按钮禁用或弹层反馈，不因 Mock 实现而出现崩溃或无响应状态。
- 本地数据读取失败时恢复初始 Mock 数据，并保留可见的轻量提示。

3. 分别截取参考图和实现图。

## 11. 验收标准

- Xcode 16.3 下使用 Swift 6 编译通过，Deployment Target 为 iOS 17.0。
- iPhone 16 Pro / iOS 18.4 模拟器可以冷启动、重启和重复运行。
- 所有核心页面、弹层与交互状态均可到达，不存在占位空页面。
- 主要业务流程均有自动化测试，测试全部通过。
- 关键页面在 `393 × 852` 基准下的主要组件位置与尺寸误差控制在约 `±2pt`。
- 颜色、圆角、阴影、层级、文字内容和换行与参考图保持视觉一致。
- 不出现内容遮挡、底部操作被 Home Indicator 覆盖、键盘挡住输入项或返回路径中断。
- 完成多轮截图对比后，除平台字体栅格化和系统元素差异外，不存在肉眼明显的布局偏差。
- 交付时附上构建结果、测试结果、已验证流程和关键对比截图路径。

## 12. 风险与控制

- **Web 与 SwiftUI 字体渲染不同：** 使用相同字号、字重、行高和宽度约束，以叠图结果调校。
- **原型大量固定布局：** 先保证 393 × 852 基准，再验证较小和较大 iPhone，不通过缩放整页规避适配。
- **页面和弹层数量较多：** 先建立设计系统和状态模型，再按核心流程分批实现，避免视觉实现分叉。
- **Mock 状态难以复现：** 提供确定性种子数据和开发重置入口，每个 UI 测试独立恢复状态。
- **持续视觉调整引入回归：** 每完成一个页面建立截图基线，修改设计令牌后重新执行全部关键截图。

## 13. 完成定义

只有同时满足以下条件才视为完成：

1. 功能范围完整实现。
2. 编译和自动化测试通过。
3. iPhone 16 Pro 模拟器中的核心流程全部走通。
4. 关键页面完成 Web 与 SwiftUI 截图对比并迭代到验收阈值。
5. 不把尚未实现或未经验证的页面描述为完成。
